   - **场景 / Scene**（左上）：一棵「节点树」，显示这个场景里有哪些节点。
   - **检查器 / Inspector**（右侧）：选中某个节点后，在这里改它的属性（位置、颜色、速度……）。

   - **脚本（Script）**：挂在某个节点上、控制它行为的 `.gd` 代码文件。
   - **信号（Signal）**：节点之间「我发生了一件事」的通知，别人连上去就能收到。

## Day 2 · 角色能显示

### 今天做什么
用四个节点把「玩家」这个角色搭出来：

| 节点 | 干什么用的 | 类比 |
|---|---|---|
| `CharacterBody2D` | 角色的**身体**，负责物理移动和碰墙 | 木偶的躯干 |
| `Sprite2D` | 负责**画出来**（先用纯色方块占位，别去搞美术） | 给木偶穿的衣服 |
| `CollisionShape2D` | 负责**碰到东西**（矩形） | 木偶的骨架边界 |
| `Camera2D` | **镜头**，跟着角色走，勾上平滑跟随 | 摄影师 |

**顺序要点**：`CollisionShape2D` 必须是 `CharacterBody2D` 的**子节点**，`Sprite2D`、`Camera2D` 也一样（子节点会跟着父节点一起动）。

### 怎么做
1. 顶部菜单 **「场景 / Scene」→「新建场景 / New Scene」**。
2. 在弹出的窗口里选 **「其他节点 / Other Node」**，搜索 `CharacterBody2D`，创建。
3. 在左上面板把根节点改名为 `Player`。
4. 选中 `Player`，按 **Ctrl + A** 添加子节点，搜索 `Sprite2D`，创建。
   - 在检查器里找 **Texture（纹理）**，把 `icon.svg`（文件系统面板里就有）拖进去。
   - 找不到合适图也别纠结：也可以改用 `Polygon2D`，在检查器里点 **Polygon** 那一栏，画出 4 个角的点，就是一个纯色方块。**Day 2 的目标是“看得见”，不是“好看”。**
5. 选中 `Player`，**Ctrl + A** 添加 `CollisionShape2D`。在检查器里找 **Shape（形状）** → 点下拉框 → **新建 RectangleShape2D** → 展开 **Size**，改成大概 `32 × 48`。
6. 选中 `Player`，**Ctrl + A** 添加 `Camera2D`。在检查器里找 **Position Smoothing（位置平滑）** 那一段：
   - 勾上 **Enabled**；
   - **Speed** 填 `5` 左右（数字越大跟得越紧，越小越飘）。
   - （不同小版本的措辞和分组位置可能略有差异，认准 `Position Smoothing` 这个词。）
7. **Ctrl + S** 保存，文件名填 `player.tscn`，存到 `scenes/` 目录。
8. 把这个玩家场景放进关卡：打开 `scenes/level_1.tscn`，在「场景」面板里对着根节点右键 → **「实例化子场景 / Instantiate Child Scene」** → 选 `player.tscn`。
   （`level_1.tscn` 里可能已经有一个 `Player` 了，那就**别重复放**，直接用它。）
9. 让碰撞形状看得见：顶部菜单 **「调试 / Debug」→「可见碰撞形状 / Visible Collision Shapes」** 打勾。运行时会看到角色外面套一层蓝框。

### 验收标准
- [ ] `scenes/player.tscn` 存在，根节点是 `CharacterBody2D` 并已改名 `Player`。
- [ ] `Player` 下有 `Sprite2D`（或 `Polygon2D`）、`CollisionShape2D`（矩形）、`Camera2D` 三个子节点。
- [ ] `Camera2D` 的 `Position Smoothing → Enabled` 已勾选。
- [ ] 按 F5 能在画面里看到角色；打开「可见碰撞形状」后能看到角色的碰撞框。

### 对应文件
| 文件 | 作用 |
|---|---|
| `scenes/player.tscn` | 玩家场景（可复用的角色） |
| `scripts/player.gd` | 挂在 `Player` 上的脚本（Day 3、Day 4 往里加内容） |
| `scenes/level_1.tscn` | 主场景，实例化了玩家 |

### 怎么验证今天做对了
1. 在「场景」面板里点中 `Camera2D`，检查器里确认 **Position Smoothing → Enabled** 是勾上的。
2. 在「场景」面板里点中 `CollisionShape2D`，检查器里确认 **Shape** 不是 `<空 / null>`，并且 **Size** 里两个数字都不是 0。
3. 按 **F5**，看到角色方块。
4. **相机跟随**要等 Day 3 角色能动了才能直观验证（现在角色还不会动，镜头自然看不出跟不跟）——
   所以今天只要你**把节点搭对 + 形状不为空**，就算过。

> **故意留个问题给你**：Day 3 能动之后，回来把 `Camera2D` 的 `Speed` 从 `5` 改成 `1` 再跑一次，感受一下「飘」是什么感觉。这就是「调参」的第一次体验。

## Day 3 · 能跑能跳

### 今天做什么
1. 给玩家写**移动与重力**脚本。
2. 在 **「项目设置 → 输入映射」** 里加 `left`、`right`、`jump` 三个动作。
3. 实现**左右移动**和**按跳跃键起跳**。

> 本项目里这三个输入动作**早就配好了**（在 `project.godot` 的 `[input]` 段里，可以直接打开文本看），
> 玩家的移动脚本 `scripts/player.gd` 也写好了。所以你今天的重点是：**自己去项目设置里看一眼它们长什么样，然后看懂脚本的 6 个步骤。**

### 怎么做

**第一步：加输入映射（输入动作 = 给按键起个「代号」，脚本里用代号，以后换键不用改代码）**
1. 顶部菜单 **「项目 / Project」→「项目设置 / Project Settings」**。
2. 切到 **「输入映射 / Input Map」** 标签页。
3. 在**上方输入框**里敲 `left`，点 **「添加 / Add」**。
4. 新出现的 `left` 那一行右边有个 **「+」** 按钮，点它 → 在弹出的「监听输入」框里**直接按一下 `A` 键** → 确定。
5. 再点一次 `left` 行的 **「+」**，这次按 **左方向键 `←`**（这样两个键都能用）。
6. 重复同样的操作，加上：
   - `right` → `D` 和 `→`
   - `jump` → `空格` 和 `W`
   - （`restart` → `R`，方便重开，建议一起加）
7. 关掉项目设置。**这一步不需要写代码。**

**第二步：写移动与重力脚本**
1. 在文件系统面板里双击 `scripts/player.gd`，或者在「场景」面板里选中 `Player` → 右键 → **「附加脚本 / Attach Script」**（如果要新建）。
2. 脚本的结构就是四件事，对照着看 `scripts/player.gd`：
   - **加重力**：不在空中就不加；在空中就往下加速：`velocity.y += GRAVITY * delta`。
   - **读按键方向**：`var dir = Input.get_axis("left", "right")`，按左得到 -1，按右得到 +1，都不按得到 0。
   - **按跳就往上给速度**：`velocity.y = JUMP_VELOCITY`（注意这里是个**负数**，负的才是「向上」）。
   - **交给引擎去移动**：`move_and_slide()` —— 一行搞定「移动 + 撞墙停下 + 检测是否站在地上」。
3. **Ctrl + S** 保存。

**第三步：让它跑起来**
按 **F5**，A/D 走，空格跳。

### 验收标准
- [ ] 项目设置 → 输入映射 里能看到 `left` / `right` / `jump`（最好还有 `restart`）。
- [ ] 按 `A` / `D` 角色左右移动，按 `←` / `→` 也能移动（说明两组键都绑上了）。
- [ ] 按空格或 `W` 角色跳起来，落地后能再跳。
- [ ] 角色会自己往下掉（重力生效），站在平台上不会穿下去。
- [ ] 角色左右移动时，镜头平滑地跟过去（Day 2 埋的验证点，今天补上）。

### 对应文件
| 文件 | 作用 |
|---|---|
| `project.godot` | `[input]` 段就是四个输入映射（`left`/`right`/`jump`/`restart`） |
| `scripts/player.gd` | 移动、重力、跳跃（顶部一排常量 Day 4 会调） |
| `scenes/player.tscn` | 玩家场景，脚本挂在根节点上 |

### 怎么验证今天做对了
1. 打开「项目设置 → 输入映射」，逐个点开 `left` / `right` / `jump` 左边的小箭头，**应该各能看到 2 个按键**。
2. 按 **F5** 进游戏：
   - 按住 `D` 再按住 `A`，角色来回跑，不会往一个方向赖着不停。
   - 对着墙壁按住 `D`，角色**贴着墙**但不穿过去。
   - 空格连按，能连续跳（但**不允许**「按一下跳两格」的高度）。
3. 打开「输出」面板，应该能看到脚本 `_ready()` 里打印的那行 `[Player] 节点就绪…`。**看得到打印 = 脚本真的挂上去了**（这是最简单的排错手段）。

> **没反应怎么办？**
> - 按了键角色不动 → 回去看输入映射里按键是不是加在了 `left` 上（加到别的动作上了很常见）。
> - 角色像石头一样往下掉穿地板 → 检查 `CollisionShape2D` 的 `Shape` 是不是空的，以及平台有没有碰撞。
> - 「输出」里没有打印 → 脚本没挂到 `Player` 节点上。

## Day 4 · 手感调优（本计划性价比最高的一天）

### 今天做什么
1. 调 **重力 / 跳跃速度 / 空中控制系数**。
2. 加 **土狼时间（coyote time）**。
3. 加 **跳跃缓冲（jump buffer）**。

计划原话：**这两点能让手感从「很烂」变「挺顺」。**

### 先用人话解释这两个词

#### 土狼时间（Coyote Time）
名字来自动画片：那只土狼跑出悬崖之后，**要等它低头看一眼才发现自己该掉下去了**。

游戏里也一样。如果严格按物理来：**你的脚一离开平台边缘，就立刻不能跳了**。
但玩家的手比眼睛慢 1–3 帧（60 帧/秒下大约 0.02–0.05 秒），所以会出现——

> 玩家心里想：「我明明**还在**边缘上，我按了跳，凭什么不跳？！」 → 感觉「这游戏很僵」「按键不灵」。

**土狼时间的做法**：离开地面之后，**再给 0.1 秒（≈ 6 帧）的「还算你在地上」的宽限期**。这 0.1 秒内按跳，照样起跳。

- 效果：边缘跳跃、连续跳小平台时，**成功率明显上升**，玩家不会觉得被系统坑。
- 在 `scripts/player.gd` 里，这件事就是两行：`_coyote` 这个变量一直在记录「离地多久了」，跳跃条件里判断 `_coyote < COYOTE_TIME`。

#### 跳跃缓冲（Jump Buffer）
反过来的情况：玩家**提前按了跳**，但人还在空中、**还没落地**，严格判定就会把这次按键丢掉。

> 玩家心里想：「我**按了**！它不跳！」 → 然后他怪自己的键盘。

**跳跃缓冲的做法**：按跳的时候**先不判断能不能跳**，只是**把这次「意图」记下来 0.1 秒**（`_buffer = 0.0`）；
等真正落地的那一刻，如果这 0.1 秒内按过跳，就**自动补上这一跳**。

- 效果：连跳、快速落地再起跳变得「跟手」，弹跳节奏顺。
- 在 `scripts/player.gd` 里，跳跃条件里判断 `_buffer < JUMP_BUFFER`。

#### 为什么这两个加起来就「变顺」
| | 严格判定 | 加了土狼时间 + 缓冲 |
|---|---|---|
| 边缘起跳 | 常常跳不出来，玩家觉得被坑 | 0.1 秒内都算数，跟手 |
| 落地连跳 | 按键被丢掉，节奏断 | 落地自动补跳，节奏顺 |
| 玩家感受 | 「这游戏不听话」 | 「我按什么它做什么」 |

**这两个功能不加任何新内容、不画一张图，却贡献了最大的手感提升** —— 所以计划特意把它单独排成一天。

### 怎么做
1. 打开 `scripts/player.gd`，看文件**最上面那一排常量**（Day 4 的活就是调它们）。
2. 一次**只改一个数字**，**Ctrl + S** 保存，按 **F5**，跳 5 次，凭感觉记一句话。
3. 照着下面的表调（默认值是项目里现在的值）：

| 参数（`scripts/player.gd` 顶部） | 默认值 | 它控制什么 | 想更「顺/宽容」往哪调 | 调过头会怎样 | 建议范围 |
|---|---|---|---|---|---|
| `SPEED` 水平最大速度 | `220` | 跑多快 | 调大 | 太快刹不住，跳小平台容易冲过头 | 180 – 280 |
| `JUMP_VELOCITY` 起跳速度 | `-430` | 跳多高（**负数是向上**，这个符号别删） | 数字更负 = 跳更高 | 太高会飞出屏幕、跳过头顶的平台 | -350 – -520 |
| `GRAVITY` 重力 | `1150` | 往下拽的力 | 调大 = 落得更快更「沉」 | 太大跳起来像贴地，跳跃高度被吃掉 | 900 – 1500 |
| `FALL_MULTIPLIER` 下落额外重力倍率 | `1.35` | 让**下落比上升快**（平台跳跃的经典小技巧） | 调大 = 下落更利落 | 太大像自由落体，失去滞空感 | 1.0 – 1.8 |
| `COYOTE_TIME` 土狼时间 | `0.10` | 离地后还能补跳多久（秒） | 调大 = 更宽容 | 太大会出现「悬空跳」，看着像穿帮 | 0.06 – 0.15 |
| `JUMP_BUFFER` 跳跃缓冲 | `0.10` | 提前按跳被记住多久（秒） | 调大 = 更宽容 | 太大 = 明明不想跳却自己跳了 | 0.06 – 0.15 |
| `AIR_CONTROL` 空中控制系数<br>（计划里提到的第三项） | 项目当前没有这个常量，**需要你自己加一行** | 在空中时左右移动的响应比例 | `1.0` = 空中和地面一样灵活；`0.7` = 空中略笨重、更有「重量感」 | 太小会觉得在空中「推不动」 | 0.6 – 0.8 |

> **`AIR_CONTROL` 怎么加**（这是计划里点名的第三项，项目脚本里目前是「空中直接等于地面速度」）：
> 在顶部常量区加一行 `const AIR_CONTROL := 0.75`，
> 然后把脚本里第 5 步那行 `velocity.x = dir * SPEED` 改成
> `velocity.x = dir * SPEED if is_on_floor() else dir * SPEED * AIR_CONTROL`。
> 改完多试几次，感受「空中不那么好控制」和「空中完全听话」的差别。
> （不改也行 —— 这只是让你体验「空中控制系数」是什么。）

### 三次调参的推荐配方
1. **先调「跳多高」**：觉得跳不上目标平台 → 把 `JUMP_VELOCITY` 从 `-430` 试到 `-470` / `-500`。
2. **再调「落得快不快」**：觉得整个人像在月球上飘 → 把 `GRAVITY` 调到 `1300`，或把 `FALL_MULTIPLIER` 调到 `1.5`。
3. **最后调「宽容度」**：还是偶尔跳不出来 → 把 `COYOTE_TIME`、`JUMP_BUFFER` 一起从 `0.10` 调到 `0.12`。

把每次的改动填进这张小表（抄到纸上或用记事本）：

| 第几次 | 改了哪个参数 | 从 → 到 | 试完的一句话感受 | 保留还是改回 |

- [ ] 能从平台边缘**跳出去再跳回来**（土狼时间生效）。
- [ ] 从高处落地，在**快落地前**按跳，落地瞬间**自动起跳**（跳跃缓冲生效）。
- [ ] 自己动手改过至少 3 个参数，并说得出每个参数改了之后的感受。

### 怎么验证今天做对了（可操作的实验）

**实验 A：证明土狼时间真的在工作**
1. 站到平台边缘，**往平台外面走**，在脚离开边缘的**瞬间**按空格。
2. 应该能跳起来 → 土狼时间生效。
3. 打开 `scripts/player.gd`，把 `COYOTE_TIME` 从 `0.10` 改成 `0.001`，保存，F5，重复第 1 步。
4. 现在应该**几乎跳不出来**了 → 反向证明了它的作用。
5. **（重要）改回 `0.10`**。

> ⚠️ **不要把它改成 `0.0`**。脚本里的判断是 `_coyote < COYOTE_TIME`，
> 而站在地上时 `_coyote = 0.0`，`0.0 < 0.0` 是假的 —— 结果会变成**连站在地上都跳不起来**。
> 想「关掉」这个功能，就把它改成 `0.001` 这种极小值。

**实验 B：证明跳跃缓冲真的在工作**
1. 从高一点的地方跳下来，在**快要碰到地面但还没碰到**的时候按空格。
2. 落地的一瞬间应该**自动弹起来** → 缓冲生效。
3. 把 `JUMP_BUFFER` 改成 `0.001`，F5，重复第 1 步：这次落地后只会傻站着。
4. **（重要）改回 `0.10`**。
   （同理，`JUMP_BUFFER` 也别改成 `0.0`，否则连地面都跳不起来。）

**实验 C：证明参数确实在起作用**
1. 把 `GRAVITY` 从 `1150` 改成 `500`（一半），F5，跳一下 —— 会明显「飘」。
2. 改成 `2000`，F5，跳一下 —— 会明显「沉」，跳不高。
3. 改回 `1150`。

## Day 5 · 地面与平台

### 今天做什么
1. 用 `StaticBody2D` 做**固定平台**。
2. 用 `TileMapLayer` 画**砖墙背景地面**。
3. 确认**不会穿墙、不会卡在角落**。

### 怎么做

**A. 固定平台（`StaticBody2D`）**
1. **「场景」→「新建场景」** → 其他节点 → 搜索 `StaticBody2D` → 创建。
2. 给它加两个子节点：
   - `CollisionShape2D`：检查器里 **Shape** → 新建 **RectangleShape2D**，`Size` 按平台大小填（比如 `160 × 24`）。**这是「实心」的部分。**
   - `Sprite2D`（或 `Polygon2D`）：负责**看得见**。用 `Polygon2D` 画个矩形、改 **Color** 成冰蓝色最省事。
3. **Ctrl + S** 存成 `scenes/platform.tscn`。
4. 打开 `scenes/level_1.tscn`，在「场景」面板里对着根节点右键 → **「实例化子场景 / Instantiate Child Scene」** → 选 `platform.tscn`。
5. 重复第 4 步，摆 3–5 块平台：用 **W（移动模式）** 拖到合适位置；在检查器里改 **Position** 的 X/Y 也能精确摆放。
   **一个场景可以反复实例化** —— 这就是 Day 1 说的「场景可复用」。

**B. 砖墙背景地面（`TileMapLayer`）**
> Godot 4.3 之后用 `TileMapLayer` 替代了旧的 `TileMap` 节点。**找不到 `TileMapLayer` 就找 `TileMap`**（不同版本可能略有差异）。
1. 在 `level_1.tscn` 里，**Ctrl + A** 添加 `TileMapLayer`。
2. 在检查器里找 **Tile Set（图块集）** → **新建 TileSet**。
3. 把一张砖墙/冰雪纹理图拖进文件系统面板的 `assets/` 目录（先随便找一张也行），
   然后把这张图**拖到 TileSet 面板**里 —— Godot 会问图块尺寸（比如 16×16 / 32×32），按图的实际大小填。
4. 编辑器下方会出现 **「TileMap / 图块」** 面板，选一个图块，在 2D 视图里**用鼠标画**就行。
5. 画的时候留意：TileMapLayer 的碰撞要在 TileSet 里给图块加**物理层**才会「实心」。
   - **新手友好做法**：`TileMapLayer` **只当好看的背景**，实心碰撞交给 `StaticBody2D` 平台去做。
     这样你不用折腾 TileSet 的物理层，也不会出现「明明画了地却掉下去」。
   - 想学物理层：在 TileSet 面板里选 **「物理层 / Physics Layers」→ 添加元素**，再在 **「图块 / Tiles」** 里给图块画上碰撞多边形。

**C. 防穿墙 / 防卡角落（检查项）**
1. 顶部菜单 **「调试」→「可见碰撞形状」** 打勾。
2. 让角色贴着每一个平台边缘走，看碰撞框有没有**插进平台里**。
3. 把角色的 `CollisionShape2D` 的 `Size` **调小一点点**（比如从 32 改成 30），
   看卡角落的问题会不会好一些 —— 这是最常用的土办法。

### 验收标准
- [ ] `scenes/platform.tscn` 存在，根节点是 `StaticBody2D`，带 `CollisionShape2D` 和可见图形。
- [ ] `level_1.tscn` 里**同一份 `platform.tscn` 被实例化了不止一次**（说明你懂了「场景复用」）。
- [ ] 有 `TileMapLayer` 画的砖墙背景地面（哪怕只画了几格）。
- [ ] 角色站在平台上不会掉下去，跑向墙壁不会穿过去。
- [ ] **贴着墙角起跳，不会被卡住动不了**。

### 对应文件
| 文件 | 作用 |
|---|---|
| `scenes/platform.tscn` | 可复用的固定平台（`StaticBody2D`） |
| `scenes/level_1.tscn` | 关卡 1 的场景，摆平台 + 背景地面 |
| `scripts/levels/level_1.gd` | 关卡 1 的脚本（Day 11 会正式用到） |

### 怎么验证今天做对了
1. 用「可见碰撞形状」跑一遍：确认每块平台的碰撞框和你看得见的图形**基本重合**（差得太多会「看起来浮空却踩得住」）。
2. 做一个「压力测试」：**贴着每一堵墙按住方向键 3 秒**，然后跳。
   - 应该是：贴着墙滑动，跳得起来 → 正常。
   - 如果是：整个人不动了、跳也不跳 → **卡墙 bug，今天必须修**。
3. 从最高处直接掉下来砸在平台上，**不应该穿过去**（如果穿过去了，说明平台碰撞太薄，把 `Size` 的高度从 24 加到 32 试试）。
4. 按 `R` 重开，场景恢复正常。

> **避坑提醒**：Day 5 只做「地面和平台」。**今天不要加火焰、不要加移动平台** —— 那是 Day 8、Day 9 的事。

## Day 6 · 死亡与重生

### 今天做什么
1. 在关卡**底部**放一个 `Area2D` 当**掉落死亡区**。
2. 碰到就**回到检查点位置**。
3. 加**检查点**节点，碰到后**更新复活点**。

> 今天是你**第一次真正用「信号」**（Day 1 学的第 4 个概念）。
> 信号就是「我发生了一件事」的通知：死亡区喊「有人掉进来了」，关卡脚本收到后处理。

### 怎么做

**A. 掉落死亡区**
1. 打开 `scenes/level_1.tscn`，**Ctrl + A** 添加 `Area2D`，改名 `DeathZone`。
2. 给它加 `CollisionShape2D`：**Shape** → 新建 **RectangleShape2D**，
   `Size` 拉成**横跨整个关卡宽度**、高度不用大（比如 `3000 × 200`），
   然后把它**拖到关卡最底下**（比所有平台都低，掉下去必定经过它）。
3. 给 `DeathZone` 附加脚本 → 存成 `scripts/death_zone.gd`。
4. **连接信号**（这是今天的关键动作）：
   - 选中 `DeathZone`，看右侧面板切到 **「节点 / Node」** 标签页；
   - 在列表里找到 **`body_entered`**，**双击**它；
   - 弹出框里选接收方（比如父节点 `Level1`），点 **「连接 / Connect」**；
   - 编辑器会**自动帮你生成一个空的回调函数** `_on_body_entered(body)`，你在里面写处理逻辑。
   - （也可以右键节点 → **「连接信号 / Connect Signal」**，效果一样。）
5. 处理逻辑三件事：
   - 判断进来的 `body` **是不是玩家**（比如 `if body is CharacterBody2D:` 或判断节点名/分组）；
   - 让单例记录一次死亡：`GameState.add_death()`（`scripts/autoload/game_state.gd`）；
   - 把玩家坐标设回复活点：`player.global_position = GameState.spawn_point`。

**B. 检查点**
1. 新建场景：根节点 `Area2D`，改名 `Checkpoint`，加 `CollisionShape2D`（矩形，比玩家稍大一点）。
2. 再加一个可见图形（`Polygon2D` 或 `Sprite2D`），方便区分「这个已经碰过了」——
   碰到后把颜色从灰色改成亮蓝，是最直观的做法。
3. 附加脚本 `scripts/checkpoint.gd`（`scenes/checkpoint.tscn` 保存场景）。
4. 用**和死亡区一样的方法**连接 `body_entered` 信号：
   碰到玩家时把 `GameState.spawn_point` 更新成**这个检查点的坐标**。
5. 把这个检查点场景**实例化**到关卡里，摆在「比较容易死的位置前面」。
6. 全局状态放在 `scripts/autoload/game_state.gd` 里（一个**单例 / Autoload**：项目里所有脚本都能访问的公共储物柜）。
   - 如果这个单例还没出现在项目里：**「项目设置 → 自动加载 / Autoload」** 标签页里，
     把脚本路径加进去、节点名填 `GameState`，点 **添加**。
   - 全局信号总线是 `scripts/autoload/events.gd`，跨场景的通知都从它走。

### 验收标准
- [ ] 关卡底部有一个横跨整个关卡的 `Area2D` 死亡区，掉到最下面必定触发。
- [ ] 掉下去之后**自动回到出生点**（不是卡在底下、也不是无限下落）。
- [ ] 死亡次数会 **+1**（Day 10 会把这个数字显示在屏幕上）。
- [ ] 先碰到检查点、再掉下去，**回到的是检查点位置**，不是最初的出生点。
- [ ] 检查点被碰过之后有**视觉变化**（颜色变了/亮起来了），玩家知道自己已经存档了。

### 对应文件
| 文件 | 作用 |
|---|---|
| `scripts/death_zone.gd` + `scenes/death_zone.tscn` | 掉落死亡区 |
| `scripts/checkpoint.gd` + `scenes/checkpoint.tscn` | 检查点 |
| `scripts/autoload/game_state.gd` | 单例：复活点、死亡次数、用时、进度（所有关卡共用） |
| `scripts/autoload/events.gd` | 单例：全局信号总线 |
| `scripts/autoload/sfx.gd` | 单例：音效（Day 12 用到） |
| `scripts/player.gd` | 死亡时要把玩家坐标设回复活点，顺手在这里加一个 `respawn()` 函数最好 |

### 怎么验证今天做对了
1. 按 **F5**，**故意从最近的平台跳下去**：
   - 合格：画面一闪（或直接一瞬），角色回到出生点，能继续玩。
   - 不合格：角色一直往下掉、掉出屏幕看不见了 → 死亡区没接上信号，或者 `Size` 没盖住关卡宽度。
2. 先用「可见碰撞形状」确认那个大蓝框**确实在关卡最底下**。
3. **检查点测试（分三步做，才能确认是「更新」而不是「本来就在那」）**：
   1. 先什么都不碰，直接跳下去 → 应该**回到出生点**。
   2. 走过去碰一下检查点（看颜色变化），**再**跳下去 → 应该**回到检查点**。
   3. 再往前走碰**第二个**检查点，再跳下去 → 应该回到**第二个检查点**。
4. 看「输出」面板，检查点/死亡区脚本里 `print("...")` 的内容每次都能出现。

> **真·Day 6 陷阱**：如果你把 `GameState.spawn_point` 直接写成「检查点的全局坐标」，
> 而检查点本身是个 60 像素高的方块，玩家复活后会**嵌在检查点方块里**。
> 解决办法：复活点加一个向上的偏移（比如 `spawn_point + Vector2(0, -40)`），或者在检查点上方再放一个 `Marker2D` 当真正的复活位置。

## Day 8 · 移动平台

### 今天做什么
1. 用 `AnimatableBody2D` + `AnimationPlayer` 做**来回移动的平台**。
2. 让**玩家站在上面能跟着走**，不被甩下来。

### 先解释两个节点
- **`StaticBody2D`（Day 5 用的）**：永远不会动的墙和地面。
  **不能用它做移动平台** —— 它一旦动起来，引擎不会把「移动」这件事正确告诉站在上面的角色。
- **`AnimatableBody2D`**：专门为「会动、但也要能站人」而生的身体。
  它会把自己的位移**同步**给物理引擎，站在上面的 `CharacterBody2D` 就能被推着走。
- **`AnimationPlayer`**：给属性做动画的节点。今天的用法特别简单：**给平台的 `position` 做一段来回的动画**。

### 怎么做
1. 新建场景：根节点选 **`AnimatableBody2D`**，改名 `MovingPlatform`。
2. 加子节点：`CollisionShape2D`（矩形，和 Day 5 一样）+ 可见图形（`Polygon2D`，颜色换个别的，比如浅青色，好和固定平台区分）。
3. 检查器里确认 **`Sync To Physics`（与物理同步）勾选着**（默认就是勾上的，别关）。
4. 加一个 `AnimationPlayer` 子节点：
   - 在下方 **「动画 / Animation」** 面板点 **「动画 → 新建」**，起名 `move`；
   - 把时长（Length）改成比如 `3.0` 秒；
   - 选中 `MovingPlatform` 节点，在时间轴 **0 秒**处点 `position` 旁边的**钥匙图标**记录起点；
   - 把时间游标拖到 **1.5 秒**，用 **W（移动模式）** 把平台拖到**终点位置**，再点一次钥匙记录；
   - 把游标拖回 **3.0 秒**，把平台拖回**起点**，再记录一次（这样就是「来回」）；
   - 想更省事也可以只记录 0 秒和 1.5 秒两个关键帧，然后把动画的**循环模式（Loop Mode）**设为**往返 / Ping-Pong**。
5. 让动画自动播放：在 AnimationPlayer 的检查器里找 **Autoplay（自动播放）**，填 `move`；
   （或者在脚本 `scripts/hazards/moving_platform.gd` 的 `_ready()` 里写 `$AnimationPlayer.play("move")`。）
6. 点「播放」按钮预览一下，平台应该开始来回移动。
7. **Ctrl + S** 保存成 `scenes/moving_platform.tscn`，然后在关卡里实例化它。
8. **让玩家跟着走**：先在 `level_1.tscn` 里试一下 —— 大多数情况下 `AnimatableBody2D` 会自动带人。
   如果站上去被甩下来或者原地打滑，检查这三件事：
   - 平台是不是 `StaticBody2D`（**必须换成 `AnimatableBody2D`**，这是最常见的原因）；
   - `Sync To Physics` 有没有被关掉；
   - 玩家的 `scripts/player.gd` 里是不是**每一帧都在调用 `move_and_slide()`**（必须有）。
9. 想更稳一点，可以在玩家的移动脚本里判断「站在平台上时，额外加上平台这一帧的位移量」，
   这样即使平台速度很快也不会掉队（计划原文提到过这个做法）。

### 验收标准
- [ ] `scenes/moving_platform.tscn` 存在，根节点是 `AnimatableBody2D`，带 `AnimationPlayer`。
- [ ] 平台会自动来回移动，**不需要按任何键**。
- [ ] 玩家站上去之后，**跟着平台一起走**，不会被甩下来，也不会在原地打滑。
- [ ] 玩家在平台移动的过程中，还能**正常跳起来再落回平台**。

### 对应文件
| 文件 | 作用 |
|---|---|
| `scripts/hazards/moving_platform.gd` + `scenes/moving_platform.tscn` | 移动平台 |
| `scripts/player.gd` | 需要的话在这里加「跟随平台位移」的处理 |
| `scenes/level_1.tscn` | 摆放移动平台试玩 |

### 怎么验证今天做对了
1. **带人测试**：跳上平台，**双手离开键盘**（不要按任何键），盯着看：
   - 合格：跟着平台走完一整个来回，人还站在上面。
   - 不合格：平台走了人留在原地 / 人被挤下去 / 人开始抖动。
2. **跳跃测试**：站在移动中的平台上按空格起跳，落地后**还站在平台上**。
3. **反向测试**：让平台**朝你撞过来**，你应该被**推开**而不是穿过去。
4. **边界测试**：站到平台边缘（半个脚在外面），看会不会突然滑下去 ——
   如果太容易滑，把玩家碰撞盒调宽一点点，或者把平台速度调慢。

> **避坑**：今天**只做移动平台**。火焰、按钮、门都是 Day 9 的活。

## Day 9 · 危险区与机关

### 今天做什么
1. **蓝色火焰**用 `Area2D` 实现，**碰到就死亡**。
2. 加一个开关：**踩按钮后门打开**。
3. 加一个**会消失再出现的平台**（用计时器控制）。

> 今天一次加**三个**机制，看起来多，但每一个都很小。**一个一个做，做完一个就跑一次**，别三个一起写完再跑。

### 物理层提示（今天会用到）
项目里已经给物理层起了名字（在 `project.godot` 的 `[layer_names]` 里）：

| 层 | 名字 | 放什么 |
|---|---|---|
| 1 | `world` | 地面、平台、墙 |
| 2 | `player` | 玩家 |
| 3 | `hazard` | 火焰等危险物 |
| 4 | `pickup` | 可拾取物 |

**检查器的「碰撞 / Collision」那一段里有 `Layer`（我在哪一层）和 `Mask`（我要检测哪些层）：**
- 火焰的 `Area2D`：`Mask` 里**要勾上第 2 层 `player`**，否则它检测不到玩家（这是最常见的「碰了没反应」原因）。
- 玩家的 `CharacterBody2D`：`Mask` 要勾上 `world`（和平台碰撞）。

### A. 蓝色火焰（`Area2D`）
1. 新建场景：根节点 `Area2D`，改名 `Flame`；加 `CollisionShape2D`（矩形，比图形稍小一点，**判定比看起来小一点玩家会更服气**）。
2. 可见部分：用 `Polygon2D` 画一个三角形/火焰形状，颜色用**蓝色系**（比如 `#4FC3F7`）——计划里明确是**蓝色火焰**，别做红色。
3. 附加脚本 `scripts/hazards/flame.gd`。
4. 连接 **`body_entered`** 信号（Day 6 学过），逻辑：
   - 判断进来的是不是玩家；
   - 是的话 → `GameState.add_death()` → 把玩家送回复活点（和 Day 6 的死亡处理**复用同一段逻辑**最好，比如调用玩家身上的 `respawn()`）。
5. 保存成 `scenes/flame.tscn`，在关卡里实例化几个。
6. **可选但强烈建议**：火焰加一个轻微的「伸缩/闪烁」动画（`AnimationPlayer` 或脚本里用 `sin()` 改 scale），
   让玩家一眼看出**这是活的、有危险的**。静态的蓝色方块很容易被误认为是可以踩的平台。

### B. 踩按钮开门
1. **按钮**：新建场景，根节点 `Area2D`，改名 `Button`；加 `CollisionShape2D` + 可见图形（画个小方块/圆点）。
   脚本 `scripts/hazards/button.gd`：
   - 连接 `body_entered` → 判断是玩家 → 通过**全局信号总线** `scripts/autoload/events.gd` 发出「按钮被踩了」的信号；
   - 加一个 `once`（只触发一次）的判断，避免玩家站在上面反复触发。
   - 视觉反馈：踩下去时变个颜色 / 往下移几个像素（**一定要有反馈**，否则玩家不知道自己踩到了）。
2. **门**：新建场景，根节点用 `StaticBody2D`（要挡住人，所以必须是实心的）或 `AnimatableBody2D`，改名 `Door`。
   脚本 `scripts/hazards/door.gd`：
   - 在 `_ready()` 里连上 `Events` 的「按钮被踩」信号；
   - 收到后**播放开门动画**（`AnimationPlayer` 把门往上/往旁边移开），或者简单点直接 `visible = false` + 关掉碰撞。
   - **建议用动画不要用 `visible = false`**：门「滑上去」比「凭空消失」更清楚，玩家知道门开了。
3. 保存成 `scenes/button.tscn`、`scenes/door.tscn`，在关卡里配套摆：**门挡住必经之路，按钮放在需要绕一下才能到的地方**。

### C. 会消失再出现的平台（`blink_platform`）
1. 新建场景，根节点用 `AnimatableBody2D`（它要能站人），改名 `BlinkPlatform`；加 `CollisionShape2D` + 可见图形。
2. 脚本 `scripts/hazards/blink_platform.gd`：用一个 `Timer` 或计时变量循环：
   - **出现（实心）若干秒 → 预警闪烁约 0.3 秒 → 消失（关掉碰撞 + 变半透明）若干秒 → 再出现**。
3. **关键的手感要求：消失之前必须先闪一下。** 直接消失会让玩家觉得「这游戏耍赖」；
   闪 0.3 秒等于给了玩家「快跑」的提示。计划里说「不要考验玩家耐心」，这里就是具体做法。
4. 建议参数：出现 2 秒 / 预警闪 0.3 秒 / 消失 1.5 秒，循环。

### 验收标准
- [ ] 碰到蓝色火焰 → 玩家死亡、回到检查点、死亡次数 +1。
- [ ] 站在火焰**旁边**（不接触）不会死（判定别做太大）。
- [ ] 踩下按钮 → 门打开（有动画或有明显变化），**而且开过就保持开着**。
- [ ] 会消失的平台：**先闪 0.3 秒再消失**，消失期间人站上去会掉下去，之后会重新出现。
- [ ] 三个机制**互不干扰**：火焰旁边放按钮/门也不会出问题。

### 对应文件
| 文件 | 作用 |
|---|---|
| `scripts/hazards/flame.gd` + `scenes/flame.tscn` | 蓝色火焰危险区 |
| `scripts/hazards/button.gd` + `scenes/button.tscn` | 踩踏按钮 |
| `scripts/hazards/door.gd` + `scenes/door.tscn` | 门 |
| `scripts/hazards/blink_platform.gd` + `scenes/blink_platform.tscn` | 会消失再出现的平台 |
| `scripts/autoload/events.gd` | 按钮 → 门 之间的全局信号总线 |

### 怎么验证今天做对了
1. **火焰**：站着不动让火焰碰你 → 死。刻意贴着火焰边缘走一圈 → **不该死**。
2. **按钮和门**：
   - 先**不去**踩按钮，直接走到门前 → 门挡着，过不去。
   - 去踩按钮 → 听到/看到反馈 → 门打开 → 走回去 → **能过去了**。
   - 再踩一次按钮 → 门**不会**又关上（一次性开关）。
3. **闪烁平台**：
   - 站上去不动，等它闪 → 消失 → 你掉下去。**这说明判定真的关了**（如果站在空中不掉，说明碰撞没关）。
   - 等它重新出现 → 还能踩上去。
4. **组合测试**：把火焰放在闪烁平台上（Day 11 的关卡 2/3 会这么摆），确认「平台消失时火焰也不会踩到玩家」或者「掉进火焰会死」，行为符合你的预期。
5. 打开「输出」面板，看看有没有**红字报错**（尤其是 `Invalid call` 之类 —— 通常是因为门的信号连了两次，或者单例名字写错了）。

4. 在 `scripts/level_base.gd` 里监听 `Esc`（或你自己选的键）：`get_tree().paused = true` + 显示菜单。

4. 关卡终点放 `Area2D`，脚本 `scripts/finish_flag.gd`：碰到玩家 → 停在通关界面 →

- [ ] 重开之后场景**完全恢复**（死掉的机关回到初始状态、玩家回到出生点）。
- [ ] 走到终点旗子 → 出现**通关界面**，显示用时和死亡次数。

| 文件 | 作用 |
|---|---|
| `scenes/ui/main_menu.tscn` | 开始界面 |
| `scenes/ui/hud.tscn` | 游戏内 HUD（关卡 / 死亡数 / 用时） |

| `scripts/level_base.gd` | 每关继承它，统一处理暂停 / 重开 / 通关 |

### 怎么验证今天做对了
1. **完整流程走一遍**：主菜单 → 开始 → 玩 → 通关界面 → 下一关。
2. **暂停测试**：暂停之后，**游戏里的角色必须冻住**（按 A/D 不动、跳不起来），
   同时暂停菜单的按钮**能点**。这两个条件同时满足才算对。
3. **重开一致性测试**：故意踩一次按钮把门打开 → 按 `R` 重开 →

4. **死亡次数测试**：记下数字 → 掉进死亡区 3 次 → 数字应该正好变成「原值 +3」。
5. **`R` 键和按钮两条路都要试**：计划要求的是 `reload_current_scene()` 快速重开，
   键盘 `R` 和界面按钮最好都通向同一个函数（这样行为不会不一致）。

> **设计小提醒**：重开时**死亡次数要不要清零**，你自己定 —— 但一定要**前后一致**，
> 不能按 `R` 清零、点按钮不清零（玩家会觉得游戏坏了）。建议：**重开保留死亡次数**，
> 只有回到主菜单或换关才清零，这样「死亡次数」才是一个有意义的成绩。

## Day 11 · 做 3 个关卡

### 今天做什么
按计划的难度曲线，做**三个越来越难的关卡**，每关 **30–60 秒**能通关：

| 关卡 | 内容 | 目标 |
|---|---|---|
| 关卡 1 | **只练跳，无危险** | 让玩家学会「跳」本身，永远不会死 |
| 关卡 2 | **加火焰** | 学会「躲」 |
| 关卡 3 | **加移动平台 + 开关门** | 学会「等时机」和「配合机关」 |

### 怎么做
1. 每一关建一个独立场景：`scenes/level_1.tscn`、`scenes/level_2.tscn`、`scenes/level_3.tscn`。
   （`level_1.tscn` 已经有了，Day 2–9 一直在改它。）
2. **先用 `level_1.tscn` 复制一份**做原型：在文件系统面板里右键 `level_1.tscn` → **「复制 / Duplicate」**（或 `Ctrl+D`），
   改名成 `level_2.tscn`，再双击打开改内容。**这样比从零摆快 10 倍。**
3. 每一关的脚本放在 `scripts/levels/` 下：`level_1.gd` / `level_2.gd` / `level_3.gd`。
   - 它们都 **`extends` 通用的 `scripts/level_base.gd`**；
   - 通用逻辑（死亡、重开、暂停、通关、计时）写在 `level_base.gd` 里**写一次**；
   - 每一关的脚本里**只写这一关不一样的地方**（比如关卡 3 需要「门开了才算数」）。
4. **关卡 1（只练跳，无危险）的要点**：
   - **不要放火焰**（一个都别放）；
   - 平台间距**由近到远**：第一跳闭着眼都能过，最后一跳稍微要用力；
   - 可以放**移动平台以外**的所有安全元素：闪烁平台也别放（新手会掉下去）；
   - 检查点至少 1 个，放在中段。
5. **关卡 2（加火焰）的要点**：
   - 火焰数量 **3–6 个**就够，别铺满；
   - 每个火焰**旁边必须留出安全落脚点**；
   - 火焰与火焰之间**留出 1 秒以上的反应时间**（计划说「不要考验玩家耐心」）；
   - 关底可以用一个「必须跳过火焰」的小挑战当收尾。
6. **关卡 3（移动平台 + 开关门）的要点**：
   - **一次只引入一个新概念**：先一段纯移动平台，再一段「踩按钮 → 门开 → 冲刺过去」；
   - 门的后面**不要**马上接死亡陷阱（玩家好不容易开了门就死，会很气）；
   - 移动平台速度**比你想的再慢一点**（你自己玩熟练了，朋友第一次玩一定更慢）。
7. **每关的目标时长**：不死的情况下 **30–60 秒**。用手机秒表或看 HUD 上的用时。
   - 超过 60 秒 → **拆掉一块平台 / 挪近一点**；
   - 不到 30 秒 → 加一小段。
8. **通关顺序**：终点碰到旗子 → 解锁下一关 → 打开下一关（或回主菜单选关）。

### 验收标准
- [ ] 三个关卡场景都存在，都能用 **F6** 单独运行、单独通关。
- [ ] 关卡 1 里**一个危险物都没有**，可以「一路乱按也不会死」地走过去（这是它的设计目标）。
- [ ] 关卡 2 有火焰，且每个火焰旁边都有能站的地方。
- [ ] 关卡 3 同时有移动平台**和**「按钮开门」。
- [ ] 不死通关时间都在 **30–60 秒**之间（三个都记下来）。
- [ ] 从关卡 1 通关能进关卡 2，关卡 2 通关能进关卡 3。

## Day 12 · 美术与音效替换

### 今天做什么
1. 去免费素材站找 **2D 冰雪平台素材**（**注意授权**）。
2. 加**背景音乐、跳跃音、死亡音**。
3. 用 **`CPUParticles2D`** 做简单**雪雾粒子**，接近「冰塔」的氛围。
4. **兜底**：如果找不到合适授权的素材，项目里**已经用 Godot 内置的多边形和粒子做了无需素材的替代方案**（见下面 A 节），照样能发布。

### A. 先说你手里已经有的「零素材方案」（重要）
我们**故意**没有让这个项目依赖任何外部图片或音频文件：
- **角色、平台、火焰、门、按钮**都用 Godot **内置的多边形**（`Polygon2D`）画出来 —— 只有形状和颜色，没有贴图。
- **雪雾粒子**用 `CPUParticles2D` 当场生成（脚本 `scripts/falling_snow.gd`）。
- **音效**用 `scripts/autoload/sfx.gd` **程序化生成**（现场合成一段波形播放），**不需要任何 `.wav` / `.mp3` 文件**。

所以：
- **找不到合心意的授权素材，不算没完成 Day 12。** 只要你的游戏「能看、能听、有氛围」，就达标了。
- 这也是计划里「不要先做美术」这条坑的落实方式：**先有能玩的东西，美术永远是可替换的皮**。
- **动手替换之前，先按 F5 跑一遍并截一张图**，当作「兜底版本」的存档。换素材的过程中每换一处就跑一次，坏了能照着截图找回来。

### B. 找免费素材的站点建议
| 站点 | 有什么 | 授权情况 |
|---|---|---|
| **Kenney**（`kenney.nl`） | 2D 平台素材、UI、音效包，风格统一 | **基本都是 CC0**，不用署名，**新手首选** |
| **OpenGameArt**（`opengameart.org`） | 海量 2D 素材 | **混合授权**，每个素材页面都写了许可，**只挑 CC0 / CC-BY** |
| **itch.io 免费素材区** | 很多独立作者发布的素材包 | 每个作者自己写 License，**下载前一定读一遍** |
| **Pixabay** | 图片、音效、音乐 | 自有许可，允许商用，注意个别条目的额外限制 |
| **Freesound**（`freesound.org`） | 音效 | **混合授权**，注意区分 CC0 和 CC-BY-NC |

**搜索关键词建议**（用英文搜索命中率高很多）：
`ice platformer tileset`、`snow 2d assets`、`winter platformer`、`ice cave tileset`、`free 2d platformer sfx`。

### C. 授权注意事项（**CC0 优先**）
| 许可 | 能不能用 | 你要做什么 |
|---|---|---|
| **CC0 / 公共领域** | ✅ **最推荐** | 随便用，不强制署名（写一句感谢更体面） |
| **CC-BY** | ✅ 可以用 | **必须署名**：素材名 + 作者 + 许可 + 来源链接 |
| **CC-BY-SA** | ⚠️ 尽量避开 | 署名，而且**你的作品也要用同样的许可分享**，很麻烦 |
| **CC-BY-NC（非商业）** | ⚠️ 避开 | 一旦你想挂赞助/卖钱就侵权 |
| **CC-BY-ND（禁止改）** | ⚠️ 避开 | 不能改颜色、不能裁切、不能缩放拼图，做游戏基本没法用 |
| **来源不明 / 搜索引擎图片** | ❌ **绝对不要用** | 百度/Google 搜到的图、别人游戏里的截图 —— 全都不要 |
| **动漫 / 影视素材** | ❌ 不要用 | 通常没有可商用授权，风险很高 |

**署名怎么写**（放在 itch.io 项目页底部、或项目根目录建一个 `assets/CREDITS.md`）：
```
素材名 by 作者名，许可：CC BY 4.0
来源：<素材页面链接>
下载日期：2026-XX-XX
```
**养一个好习惯**：每下载一份素材，**立刻**把「来源链接 + 作者 + 许可 + 下载日期」记进 `assets/CREDITS.md`。
事后回头找来源是最痛苦的事，而且真出问题时这份记录就是你的证据。

### D. 替换素材（动手部分）
1. 在项目根目录新建 `assets/` 文件夹（用文件系统面板右键 → **「新建 / New」→「文件夹」**）。
   把下载的图片**直接拖进这个文件夹**（Godot 会自动导入，右下角会转一小圈）。
2. 打开 `scenes/player.tscn`，选中 `Sprite2D`，在检查器里把 **Texture** 换成新图。
   - 图太大或太小：在检查器里调 **Transform → Scale**，或者调 **Region** 裁剪，别去改源文件。
3. 同样方式替换平台、门、按钮的图形。
   - 如果原来是 `Polygon2D`：**先把 `Polygon2D` 隐藏（点眼睛图标）或删掉，再加 `Sprite2D`** ——
     两个图形叠着会很难看。
4. **切记不要动 `CollisionShape2D`**。换皮只换「看得见的部分」，碰撞形状的尺寸**保持不变**，
   否则你调好的手感会全部作废。
5. 加**背景音乐**：
   - 在关卡根节点下加 `AudioStreamPlayer`，把 **Stream** 设成音乐文件，勾**Autoplay（自动播放）**；
   - 检查器里把 **Volume Db** 调到 `-12` 左右（背景音乐**必须比音效小**，否则吵得人想关掉）。
6. 加**音效**：项目已经提供了 `scripts/autoload/sfx.gd` 这个单例，直接调用它播放即可
   （跳跃时、死亡时、通关时各一次）。想换成真实音频文件也行：加几个 `AudioStreamPlayer`，在同样的事件里 `play()`。
7. 加**雪雾粒子**：
   - 新建 `CPUParticles2D` 节点（`scripts/falling_snow.gd` 已经封装好一份可以直接用）；
   - 在检查器里调：
     - **Emission Shape（发射形状）**：选**矩形 / Box**，`Extents` 拉宽到盖住整个镜头宽度；
     - **Amount（数量）**：`50–150`（别贪多，太多会掉帧）；
     - **Lifetime（生命周期）**：`6–10` 秒；
     - **Gravity（重力）**：`(0, 20)` 左右的**轻微下坠 + 横向漂移**，才有「雪雾」感；
     - **Color**：白色，透明度（Alpha）调到 `0.4–0.7`，**不要纯白不透明**，否则像下冰雹。
   - **用 `CPUParticles2D` 而不是 `GPUParticles2D`**：本项目用的是**兼容模式（`gl_compatibility`）渲染器**，
     而且目标是浏览器，`CPUParticles2D` 在各平台都最稳。
8. 粒子放在关卡根节点下（**不要**放在玩家身上），给个**很靠后的 `Z Index`** 让它当远景，别挡住玩家。

### 验收标准
- [ ] 至少替换了**角色**和**平台**的图形（或者你决定保留多边形方案，也要在复盘里写清楚为什么）。
- [ ] 有**背景音乐**，且音量**明显小于**音效。
- [ ] **跳跃、死亡、通关**三种音效都能听到（死亡音和通关音要不一样，不然分不清）。
- [ ] 有 `CPUParticles2D` 做的雪雾粒子，**看得出来在飘**，而且不挡住玩家。
- [ ] 如果用了外部素材，`assets/CREDITS.md` 里记录了来源和授权。
- [ ] 按 F5 帧率**没有明显下降**（原本流畅，现在依然流畅）。

| 文件 | 作用 |
|---|---|
| `scripts/falling_snow.gd` | 雪雾粒子逻辑（`CPUParticles2D`） |
| `scripts/autoload/sfx.gd` | 程序化音效单例（**不需要外部音频文件**） |

### 怎么验证今天做对了
1. **氛围测试**：按 F5，站在起点不动看 10 秒 —— 雪应该在飘，音乐应该在放，画面看起来是「冰天雪地」。
2. **音效测试**：跳一次（有跳跃音）、死一次（有死亡音）、通关一次（有通关音）。
   **三种声音必须能区分开。**
3. **帧率测试**：顶部菜单 **「调试 / Debug」→「显示器 / Monitors」** 打开监视器，看 **FPS**。
   - 目标：稳定在 **60** 左右，粒子全开也不掉太多。
   - 掉帧了就先减粒子数量（`Amount` 从 150 降到 60），再考虑系统资源。
4. **音量测试**：把系统音量调到平时听歌的大小，玩 3 分钟 —— **背景音乐不该让你想关掉声音**。
5. **授权留痕测试**：打开 `assets/CREDITS.md`，随便挑一行，点链接能不能打开原素材页面。
   能打开 = 你的记录是可用的证据。
6. **兜底检验**：回想一下 —— 就算**把所有外部素材删掉**，游戏还能不能跑？
   如果答案是「能」（因为碰撞和逻辑都不依赖素材文件），说明你把「皮」和「骨架」分开了，这是最健康的做法。

## Day 13 · 测试与修 bug

### 今天做什么
1. **找 3 个朋友试玩**，记录他们卡在哪。
2. 修**高频问题**（跳不上去、卡墙、复活错、按钮没反应）。
3. **降低难度**，别考验玩家耐心。

### 怎么做
1. **准备一份「可玩的版本」**：今天可以让朋友玩你机器上的版本（按 F5），或者用 Day 14 的方法先导出 Web 版发链接
   （很多人会想先发布再测试，但计划把导出放在 Day 14 —— 按计划来，今天用**本机**或者先偷偷导出一版自己用都行）。
2. **测试脚本（照着念给朋友听）**：
   - 「你随便玩，我不会教你怎么操作，你卡住了就说一声。」——**不要提前教按键**。
     看他多久自己发现 A/D 和空格，这个信息极其宝贵（如果他要 1 分钟才发现，说明**主菜单的操作提示不够明显**）。
   - 「你玩的时候**不看我**，我也不说话。」—— 你一解释，bug 就被你掩盖了。
   - 「卡住了就停一下，我记一下。」—— 卡住的**确切位置**比什么都重要。
3. **打印/抄写下面的测试记录表**，每个朋友一张。
4. **汇总**：三张表放在一起看，**3 个人都遇到的问题优先级最高**。
5. **修复顺序**：
   1. 先修「**所有人都过不去**」的地方（这是真正的卡关）；
   2. 再修「**2 个人都提到**」的问题；
   3. 只有 1 个人提到的问题，看心情修（可能只是他的操作习惯）。
6. **降低难度的具体手段**（挑着用）：
   - 平台**加宽**；
   - 平台之间**挪近**；
   - 火焰**减少数量** / 挪到不那么关键的位置；
   - 检查点**放得更密**（宁可密，不可稀）；
   - 移动平台**减速**；
   - 闪烁平台**延长出现时间**（出现 2 秒 → 3 秒）、预警闪烁时间加长；
   - 死亡惩罚**只回到检查点**，不扣时间、不扣命、不重开整关；
   - 关卡 1 **再简化一点**（它是给新手的第一印象）。
7. 每修一个就**重新测一次**，把表格里的「是否已修」改成「✅ 已修 + 日期」。
8. 修完再让**同一个朋友**玩一遍 —— **同一个人的前后对比，比找第四个人更有价值**。

## Day 14 · 导出发布

### 今天做什么
1. 用 Godot 导出 **Web 版本**（需要**导出模板**）。
2. 上传到 **itch.io** 或 **GitHub Pages**。
3. 写一段**简介 + 一张封面图**，**发给朋友**。

> 在 **`docs/发布文案.md`** 里，到时候直接复制。

### 第一步：装导出模板（Web 导出必须先做这一步）
Godot 的「导出」功能依赖**导出模板**这个额外下载包，**版本必须和引擎完全一致**（你现在是 **4.7.2-stable**）。

**方法 A（联网，推荐）**：
1. 编辑器顶部菜单 **「编辑器 / Editor」→ 找「管理导出模板 / Manage Export Templates」**
   （不同版本位置可能略有差异，也可能在 **「项目 / Project」** 菜单里，找不到就在这两个菜单里翻一下）。
2. 点 **「下载并安装 / Download and Install」**，等它下完（几百 MB，看网速）。

**方法 B（离线 / 下载太慢）**：
1. 去 Godot 官网下载页，找 **Export Templates** 那一栏，下载 `Godot_v4.7.2-stable_export_templates.tpz`。
2. 打开用户数据目录：在文件资源管理器地址栏输入 `%APPDATA%\Godot\export_templates\`（回车）。
   - 里面应该有个类似 `4.7.2.stable` 的文件夹（**版本号必须对得上**，不同版本目录名可能略有差异）。
   - 把 `.tpz` 里的 `templates` 文件夹内容放进去（`.tpz` 其实就是个 zip，可以改名成 `.zip` 解压）。
3. 也可以在编辑器里 **「编辑器 / Editor」→「编辑器设置 / Editor Settings」** 里找 **导出模板路径** 的选项改成你自己的目录（不同版本措辞可能略有差异）。
4. 装好后，回到「管理导出模板」窗口，应该显示**当前版本已安装**。

> ⚠️ **最常见的失败原因**：模板版本和引擎版本不一致（比如引擎是 4.7.2，模板是 4.4）。
> 导出时会警告「模板缺失 / 版本不匹配」，**换成一模一样的版本号**就行。

### 第二步：导出 Web 版本
1. **先确认渲染器**：本项目用的是**兼容模式**（`project.godot` 里有 `renderer/rendering_method="gl_compatibility"`），
   这是浏览器里**最稳**的选择，**别改成 Forward+ / Mobile**（Web 上可能黑屏）。
2. 顶部菜单 **「项目 / Project」→「导出 / Export」**。
3. 点 **「添加 / Add…」** → 在列表里选 **「Web」** → 确定。
4. 在 **「导出路径 / Export Path」** 里选一个**空的新文件夹**，文件名写 `index.html`。
   - **不要**导到项目目录里（会污染项目）；
   - **不要**覆盖别的东西。建议建一个 `导出/web/` 或桌面上的 `冰塔跳跃-web/` 文件夹。
5. 看一下右侧的选项，重点关照这几个（**不同版本的分组和措辞可能略有差异，看到关键词就对了**）：
   - **资源 / Resources**：勾选需要打包的场景；干脆点「导出所有资源 / Export All Resources」最省事。
   - **线程支持 / Thread Support**（有时叫 Extensions Support 或类似名字）：
     **建议关掉**。开启线程需要服务器发送跨源隔离响应头（`SharedArrayBuffer` 那一套），
     上传到 GitHub Pages 会很麻烦；关掉之后普通静态托管就能跑。
     代价是性能略降 —— 对一个 2D 小游戏**完全无所谓**。
   - **渲染器 / Renderer**：保持兼容模式（`gl_compatibility`）。
6. 点 **「导出项目 / Export Project」**，等它跑完。
7. 导出成功的文件夹里应该有这些文件（文件名取决于你起的名字）：

| 文件 | 是什么 |
|---|---|
| `index.html` | **入口**，别人点开的就是它 |
| `index.js` | 启动代码 |
| `index.wasm` | 引擎本体（**最大**的那个文件） |
| `index.pck` | 你的游戏数据（场景、脚本、资源） |
| `index.icon.svg` | 网页标签页的小图标 |

   **这几个文件必须放在同一个文件夹里一起上传，缺一个都跑不起来。**

### 第三步：本地预览（**必须用 HTTP 服务器，不能双击 html**）
**为什么不能双击 `index.html`？**
双击是 `file://` 协议，浏览器出于安全限制**会拦住** `index.pck` / `index.wasm` 的读取，
你会看到**黑屏**、加载条卡住、或者控制台一堆红字。**这不是导出失败，是打开方式不对。**

任选一种方式起一个本地服务器：

| 方式 | 前提 | 命令（在导出文件夹里打开 PowerShell / CMD 执行） | 然后用浏览器打开 |
|---|---|---|---|
| Python | 装了 Python | `python -m http.server 8000` | `http://localhost:8000` |
| Node.js | 装了 Node | `npx serve .` | 命令行会打印出地址，通常是 `http://localhost:3000` |
| Godot 自带 | 有编辑器 | 菜单 **「远程调试 / Remote Debug」→ 找「在浏览器中运行 / Run in Browser」**（不同版本位置可能略有差异） | 它会自动起服务器并打开浏览器 |

- 想停掉服务器：在那个命令行窗口按 **Ctrl + C**。
- 想看报错：在浏览器里按 **F12** 打开开发者工具 → **「控制台 / Console」** 标签页，红字就是原因。

### 第四步：`.wasm` 的 MIME 提醒（重要）
浏览器加载 `.wasm` 文件时，**服务器必须用 `application/wasm` 这个类型返回它**（`.js` 用 `text/javascript`）。

- **不用管的情况**：Python 的 `http.server`、`npx serve`、**itch.io**、**GitHub Pages** —— 它们都已经配好了。
- **要手动配的情况**：你自己写的服务器、某些默认配置的 nginx / IIS。
  - **MIME 配错的典型症状**（在浏览器 F12 控制台里）：
    - `Incorrect response MIME type: application/octet-stream`
    - `Failed to load ... index.wasm`
    - 画面卡在加载界面不动。
  - nginx 加一行：`types { application/wasm wasm; }`
  - IIS：在网站根目录放一个 `web.config`，加一个 `.wasm → application/wasm` 的 MIME 映射。

2. 右上角头像菜单里找 **「Upload new project / 上传新项目」**（或仪表盘上的 **Create new project**）。
3. 填基础信息：
   - **Title**：`冰塔跳跃`（英文名可以写 `Ice Tower Jump`）；

## 附录 C · 卡住了怎么办（排错速查）

| 症状 | 先查这里 |
|---|---|
| 双击 exe 报 `LoadLibrary failed with error 126` | 别双击 exe，改双击 `启动Godot编辑器.bat`（强制 D3D12 后端） |
| 按了键角色不动 | 项目设置 → 输入映射，按键是不是加到了别的动作上 |
| 角色穿过地板 | `CollisionShape2D` 的 `Shape` 是不是空的；平台有没有碰撞 |
| 脚本里的 `print` 没出现 | 脚本没挂到节点上，或节点名字写错了（`@onready` 里的 `$节点名`） |
| 碰到火焰没反应 | 火焰 `Area2D` 的 **Mask** 有没有勾上玩家的物理层（第 2 层 `player`） |
| 掉下去一直往下掉 | 死亡区的 `Size` 没盖住关卡宽度，或者 `body_entered` 信号没连上 |
| 站在移动平台上被甩下来 | 平台是不是 `StaticBody2D`（要换成 `AnimatableBody2D`）；`Sync To Physics` 有没有被关 |
| 暂停后按钮点不动 | 暂停菜单根节点的 **Process Mode** 改成「当暂停时 / 总是」 |
| 导出的网页黑屏 | 是不是双击了 `index.html`（要用 HTTP 服务器）；F12 看控制台红字 |
| 控制台报 MIME / `wasm` 加载失败 | 服务器没给 `.wasm` 返回 `application/wasm`（见 Day 14 第四步） |
| 导出时提示模板缺失 | 导出模板版本必须和引擎完全一致（4.7.2-stable） |
| 项目被我改坏了 | 双击 `自检.bat`，按输出里 `❌` 的行去修 |
